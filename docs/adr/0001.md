# ADR 0001: explicit disposable VMs and separate controller policy validation

Status: accepted; Ubuntu 24.04 and AlmaLinux 9.8 ARM64 real-VM profiles validated.
See the [revision-linked results](../validation.md); publication remains pending.

## Context

The work requires genuine systemd, security-mode, package-manager and reboot
behavior on Ubuntu and AlmaLinux. The development host is macOS ARM64, and the
user prohibits host configuration changes, cloud resource creation and paid
services. Container-only tests would not establish the required OS behavior.
A safe demonstration must still be useful before allocating guest resources.

## Decision

Use repository-local Lima with Apple Virtualization.framework as the one supported
provider. Lock official ARM64 cloud images and provider/controller tooling. Limit
execution to one 2-CPU/2-GiB guest at a time and verify ownership before lifecycle
operations. Use no host mounts, no agent forwarding and no application port
forwarding. Seed guest SSH host keys through local initialization and require
strict checking from the first authenticated connection.

Keep Ansible guest desired state in one reusable `ops_baseline` role with explicit
distribution variable files and small tasks files. Validate typed values and lab
identity before mutation. Use builtin modules plus pinned `ansible.posix`; native
nftables on Ubuntu avoids another collection, while the firewalld module handles
AlmaLinux's runtime/permanent configuration without parsing mutation output.
Retain SELinux/AppArmor and use guest port 80 rather than adding a nonstandard
SELinux port mapping solely for the lab.

Reuse the role's pure input assertions in a nonprivileged localhost demo. Use
Molecule only against real provider inventories for convergence/idempotence and
verification. Keep maintenance and reboot explicitly gated, separate from ordinary
convergence. Publish evidence of what actually ran, not expected tool output.

## Consequences

The controller demo is low-resource and can reject bad configuration without any
VM, but it does not establish provisioning. Real integration remains necessary
and can be blocked by host resources or provider/platform constraints. Only the
chosen macOS ARM64 VZ provider is implemented; Linux/KVM, Intel hosts and other
hypervisors stay unverified alternatives.

Locking images/tooling makes inputs reviewable, but distribution package mirrors
remain moving dependencies without repository snapshots. The seeded host-key
method trusts the local controller/hypervisor and is not a production PKI. VM
recreation is a documented lab recovery path, while the demonstrated content
rollback is intentionally narrower than OS rollback.

## Alternatives considered

Docker-only Molecule tests are smaller but insufficient for the systemd/reboot
claims. A global Lima installation/home is convenient but would widen the resource
boundary. Cloud VMs would add cost and authorization requirements. Running the
role against the development host would violate its safety scope. None is selected.

## Validation findings incorporated

Chrony candidate validation must respect the guest's existing AppArmor policy.
The role therefore validates a root-only candidate beside the distribution's
chrony configuration and always removes that exact temporary file. Permanent
configuration installation remains atomic and reports its real desired-state
changes; successful zero-change second converges validate that distinction.

The first recorded Ubuntu reboot exposed an enabled but inactive firewall unit.
The dedicated unit is an early-boot service, so it declares `DefaultDependencies=no`
and explicit network/local-filesystem/shutdown ordering. This follows the
[systemd v255 service dependency documentation](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.service.xml),
which reserves removal of normal startup dependencies for early/late-boot services.
The unit retains explicit shutdown ordering and has no stop-time firewall flush.
Before activation, `systemd-analyze --recursive-errors=yes verify` checks the
installed unit and treats recursive verification diagnostics as failures, following
[systemd v255 analyze documentation](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd-analyze.xml).
The precise earlier boot conflict remains an inference because its full boot
transaction trace was not captured. Fresh Ubuntu verification immediately after
reboot, before repair, passed; the failed report remains archived.

Both guest profiles now pass the bounded acceptance, but only on the recorded
provider/image/architecture combinations. Reports are committed between profiles
to preserve the clean-source evidence gate; their original source revisions remain
distinct, with a shared implementation fingerprint. A development-mode run can
retain ignored diagnostics without creating publishable evidence. Neither mode
establishes production availability, external network denial, cloud compatibility
or unsupported distributions.
